2. What would have been simpler as one agent with tools

Ticket 102 is the poster child. The whole job is get_lease → list_obligations → request_payment, plus a note and a status update. One agent could do that in about 3–4 model calls. For scale, Accounting alone did the cash check and the request in 3 model calls and 9,180 tokens (Shift report, ticket 102). The real run used 3 agents, 2 handoffs, 10 model calls, and 24,880 tokens (table above). So roughly 60% of that was coordination: Boss reading and forwarding (10,198 tokens), and Facilities re-checking cash that Accounting then checked again. The same goes for a simple in-stock order like caps (Section 3), where a multi-agent run is mostly agents describing data to each other.

The bigger point is visibility. One agent working the whole board would have seen all of it at once: $3,400 − $2,400 rent − $840 invoice − $264 hoodie restock = −$104. It would have told me before I signed anything that I couldn't do all three, and asked me to choose. In my setup, every ticket is its own run: Boss starts fresh, and Accounting only knows what the handoff and its tools tell it. list_obligations did give Accounting every bill, but a restock we might need isn't a bill, so it was invisible until ticket 103. In practice, the order I clicked the tickets decided which customer got shorted.

The honest counterargument. The split bought real controls:

  • Only Accounting has request_payment and request_purchase_order. Inventory couldn't have requested the $840 even if it wanted to, so it had to hand off (Ticket 101 → Actual).
  • No agent can run execute_payment. The code refuses to even build an agent that has it, and both payments carry approved_by = Luke (Cash tab).
  • The audit trail attributes every step. I can see that request #1 was created by Accounting at delegation depth 2, two hops from Boss via Facilities, out of 163 logged events since the reset (audit_trail.json). With one do-everything agent holding every tool, I'd lose that separation of duties, which is exactly the control a real shop's bookkeeper would want.

My opinion: multiple agents earn their cost where an action carries money or crosses domains:

  • 101 (stock, then a blocked vendor, then a payment, then a customer message)
  • 103 (stock, then margin and cash, then a customer message)
  • anything that needs a human signature

They don't earn it on single-domain lookups like 102 or a cap order, where Boss's routing is pure overhead. If I rebuilt this, I'd make one "desk" agent do the reads and the first pass across all open tickets, then hand only the money decisions to a locked-down Accounting agent.

4. Three problems it CANNOT solve, and what I'd add

  1. A cash crunch with no way to bring money in. We're at $160 with $2,400 of rent due 2026-10-02 (Cash tab; Section 3).
    • Missing: the model has no revenue at all. There's no sales table, and no tool can add cash. The Yale AI Club's 8 hoodies at $50 ($400) would never show up in checking.
    • Add: a sales table; record_sale(ticket_id, sku, size, qty, unit_price), which credits checking and decrements stock; forecast_cash(days_ahead), which combines the balance, pending requests, obligations, and expected sales; and a Treasury/Forecasting agent that runs across the whole board before any ticket.
    • Safety: recording a sale is a write that changes cash, so it's human-approved like a payment, and the forecast is read-only.
  2. Actually filling orders. Today Inventory can only look.
    • Missing: there's no way to hold the 8 hoodies for the Yale AI Club, take the tee out of stock when it ships, receive the mug PO after its 3-day lead, or move desk.date_today forward. In this run, no ticket changed inventory by a single unit.
    • Add: an orders table; reserve_stock, adjust_inventory, receive_shipment(request_id) (only once today ≥ the order date + lead_days), and an advance_day tool.
    • Safety: Inventory gets write access, but only through these narrow tools, with stock adjustments and receipts going through the same approval queue. advance_day stays human-only, because whoever controls "today" controls what's overdue.
